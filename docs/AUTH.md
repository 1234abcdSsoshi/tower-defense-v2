# アカウント

進行データ（勾玉・編成・強化・技・ゴースト）をアカウントに預け、
どの端末からでも同じ続きから遊べるようにする仕組み。

**設定しなければ、この機能はまるごと眠ります。** 接続先が無い配布物では
拠点の「アカウント」ボタンも出ず、今までどおり端末内の保存だけで完全に動きます。
まず遊べること、が先です。

---

## 用意する（初回だけ）

### 1. Supabase のプロジェクトを作る

<https://supabase.com> で新しいプロジェクトを作ります。無料枠で始められます。

### 2. 表とポリシーを作る

Supabase の **SQL Editor** に [supabase/schema.sql](../supabase/schema.sql) を
そのまま貼って実行します。

最後に出る検算の行が **両方 `true`** であることを必ず確かめてください。

```
 profiles_rls | saves_rls
--------------+-----------
 t            | t
```

> **ここを飛ばすと、誰でも他人の進行データを読み書きできる状態で配ることになります。**
> anon キーは配布物に埋め込まれる前提の公開鍵なので、データを守っているのは
> 鍵ではなく、この行レベルセキュリティ（RLS）です。

### 3. 接続先を書く

`.env.example` を `.env` として複製し、Project Settings → API の値を写します。

```bash
cp .env.example .env
```

```
VITE_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
```

`.env` は Git に入りません。**`service_role` キーは絶対に書かないでください。**
あれは RLS を無視する全権限の鍵で、配布物に混ざると全ユーザーのデータが露出します。

### 4. 動かす

```bash
pnpm dev
```

拠点の足元に「アカウント」が出れば設定できています。

## 遊ぶ人から見た動き

| 場面 | 起きること |
|---|---|
| 初めて登録 | メールと合言葉で登録。確認メールを挟む設定なら、リンクを開いてからログイン |
| **初めてのログイン** | **その端末で進めた内容がアカウントへ引き継がれます** |
| 二度目からのログイン | アカウント側の進行を読み込みます（どの端末から入っても同じ続き） |
| 遊んでいるあいだ | 保存のたびに送るのではなく、2.5秒ぶんまとめて送ります |
| 画面を閉じるとき | 送り残しを流してから閉じます |
| ログアウト | 端末内の進行はそのまま残り、続けて遊べます |

### 進行が食い違ったとき

アカウント側に既に進行があると、そちらを正として読み込みます
（「どの端末から入っても同じ続き」を守るため）。

このとき、上書きする前の端末内データを `jidai.save.backup` に控えます。
取り違えたと気づいたら、ブラウザの開発者ツールから
`jidai.save.backup` の中身を `jidai.save` へ戻せます。

## 設計の線引き

- **合言葉はアプリ側で持たない。** 入力欄から `net/auth.ts` を通って
  Supabase へ渡るだけで、保存も検証もしません
- **表示名（`profiles`）と進行（`saves`）を分けてある。**
  2P で相手に見せるのは名前だけで、進行の中身を見せる理由がないため
- **進行データを対戦の判定に使わない。** 端末から送られてくる値なので
  信用できません。勝敗を突き合わせるなら、入力ログを再生して
  検証する側に寄せます（このゲームは決定論なのでそれができます）

## 2P を載せるとき

土台はここまでで揃っています。次に要るのは、

1. `profiles` の select を「認証済みなら他人の名前も読める」に広げる
   （SQL のコメントに書いてあります）
2. 対戦の記録を置く表。**入力ログとシードを預かり、勝敗はサーバ側で
   再生して決める**のが、このゲームの決定論設計に最も合った形です

`replayRun()`（[src/save/replay.ts](../src/save/replay.ts)）がその再生器です。
